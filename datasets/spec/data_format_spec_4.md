# Спецификация формата данных для парсинга (передать агенту-парсеру)

Цель: получить три JSON-файла для MVP навигатора по олимпиадам и поступлению.
Скоуп: **10 вузов × 4 профильные группы** (ИТ / Физика / Биомед / Экономика; см. справочники ниже) + релевантные им олимпиады. Точное число направлений внутри группы у каждого вуза — переменное, узнаётся в процессе парсинга (см. раздел 2), а не задано заранее.

**Формат каждого выходного файла:** JSON-объект с одним ключом верхнего уровня, значение — массив объектов из примеров разделов 2–4. Не голый массив `[...]`, чтобы можно было потом добавить метаданные (`_generated_at`, версию агента и т.п.) не ломая структуру:

```json
{ "vuz_napravleniya": [ { "...один объект из раздела 2...": "..." } ] }
{ "vuz_napravlenie_olimpiady": [ { "...один объект из раздела 3...": "..." } ] }
{ "olimpiady": [ { "...один объект из раздела 4...": "..." } ] }
```

---

## 0. Обязательные правила для ОБОИХ датасетов

1. Формат — JSON, UTF-8, кодировка дат — `YYYY-MM-DD` (ISO 8601).
2. Любой нормативный факт (льгота, порог балла, срок, статус приёма) обязан нести:
   - `source_url` — ссылка именно на ту страницу/документ, где **буквально написан этот конкретный факт**, а не на общую страницу вуза «Правила приёма» или «Приёмная кампания», внутри которой факт на самом деле лежит глубже (в приложении, в другом файле, в другом разделе). Если правила приёма — это единый PDF на много страниц, `source_url` — прямая ссылка на сам этот PDF-файл (не на страницу-лендинг, откуда на него можно перейти по клику), плюс обязательно `source_page`;
   - `source_page` — номер страницы внутри документа, если `source_url` ведёт на PDF/многостраничный документ; `null`, если источник — обычная веб-страница (тогда точность обеспечивает сам URL, при возможности — с якорем `#...` на нужный раздел);
   - `source_date` — дата, когда агент проверил источник (сегодняшняя дата парсинга, не дата публикации документа).

   **Нельзя** переиспользовать одну и ту же общую ссылку на весь блок фактов «потому что не нашли точнее». Бюджетные места, льгота победителя и льгота призёра нередко физически находятся в разных документах/разделах/страницах одного вуза — тогда у них и разные `source_url`/`source_page`. Одна и та же пара `source_url`+`source_page` допустима только если это буквально одно и то же место документа, где перечислены оба факта.
3. Если агент не нашёл факт в источнике и вынужден поставить заглушку/предположение — `is_demo: true`. Никогда не выдавать предположение за подтверждённый факт.
4. `vuz_id` — только из справочника 1.1, `profile_group` — только из справочника 1.2 (файл `profile_groups_catalog.json`). А вот `program_id`, `program_name`, `faculty`, `napravlenie_code` и `napravlenie_name` — это **результат парсинга конкретного вуза** (датасет A, раздел 2), не значение из фиксированного списка. Не подгонять реальный код направления вуза под один из `reference_codes` — если коды разные, это нормально, фиксируется настоящий код.
8. **`(vuz_id, napravlenie_code)` — НЕ уникальный ключ.** У одного вуза под одним и тем же кодом ОКСО может существовать несколько разных образовательных программ (разные факультеты/институты), и льготы по олимпиадам вуз задаёт именно на уровне программы, а не кода — у них могут быть разные списки принимаемых олимпиад. Уникальный ключ — `program_id` (раздел 2). `napravlenie_code`/`napravlenie_name` — это классификационный атрибут программы (для отчётности/фильтров по ОКСО), не идентификатор.
5. `olympiad_id` — единый ключ, общий для датасетов B и C (раздел 4). **A+B и C можно парсить полностью параллельно, разными людьми, без согласования по ходу работы** — при условии, что оба используют один и тот же **детерминированный алгоритм построения id** (раздел 4), а не придумывают слаг из названия на глаз. Если оба следуют формуле, id совпадёт сам, без переписки между исполнителями. После того как оба датасета готовы — обязательна сверка (см. чек-лист, раздел 5): join `B.olympiad_id → C.olympiad_id` не должен давать пропусков; расхождение — это баг применения формулы или пропущенная в C олимпиада, а не ожидаемая ситуация.
6. Если для пары вуз+направление факт не найден или направление вузом не ведётся — это отдельный явный статус (`not_offered` / `to_check`), а не пропущенная запись.
9. **Филиал — отдельный вуз, а не программа головного.** У филиала свои правила приёма, свои места и свои списки олимпиад, и абитуриент поступает именно туда. Поэтому `vuz_id` — это головной вуз, и в датасеты попадают только его программы: кампусы ВШЭ в Нижнем Новгороде, Перми и Петербурге, филиалы МГУ в Грозном и Севастополе, Елабужский и Набережночелнинский институты и филиал КФУ в Джизаке, Бакинский и Брянский филиалы Сеченова не читаются. Шапка секции филиала называет его «филиалом» или юрлицом головного вуза («… институт ФГАОУ ВО …») — по ней парсер секцию и отбрасывает. Нужен филиал в каталоге — это новый `vuz_id` в справочнике 1.1. Конкурсные группы для иностранных граждан — тоже не наша аудитория, их нет.
7. **Правил приёма 2027 года ещё нет** (вузы публикуют их осенью). Агент парсит действующие правила **2026 года** и обязан проставить `admission_year: 2026` в каждой записи датасета 1 — это не текущий год, а год, чьи правила фактически использованы.

### 0.1 Глобальные константы (НЕ парсить по каждому вузу)

Эти значения — общефедеральная норма из правил приёма (постановление/приказ о порядке приёма), одинаковая для всех вузов и направлений. Агент не должен искать её на сайте каждого вуза — она задаётся один раз на уровне приложения, а не в датасете:

```json
{ "diploma_validity_years": 4 }
```
(диплом победителя/призёра олимпиады действует 4 года с года получения — правило теперь не является полем в `prinimaemye_olimpiady`, см. раздел 2).

## 1. Справочники (готовые, не парсить — использовать как enum)

### 1.1 vuzy (vuz_id)
`msu`, `spbu`, `hse`, `mipt`, `itmo`, `nsu`, `kfu`, `innopolis`, `sechenov`, `kazan-gmu`

### 1.2 profile_groups (файл `profile_groups_catalog.json`)

**Важно:** направление у каждого вуза — своё, привязывать его к одному фиксированному коду ОКСО через все 10 вузов нельзя (пример: у Иннополиса нет ни 01.03.02, ни 09.03.04 — только 09.03.01 «Информатика и вычислительная техника»; код 03.03.01 «Прикладные математика и физика» почти уникален для МФТИ). Поэтому основной ключ матчинга — **`profile_group`**, а не код направления.

| profile_group | description | reference_codes (ориентир, не строгий фильтр) |
|---|---|---|
| ИТ | информатика, программирование, прикладная математика и информатика, вычислительная техника | 01.03.02, 09.03.04 |
| Физика | прикладные физика и математика, физика | 03.03.01 |
| Биомед | лечебное дело и смежные специалитеты, биология | 31.05.01, 06.03.01 |
| Экономика | экономика и смежные направления | 38.03.01 |

`reference_codes` — подсказка агенту, что искать *по смыслу* (название/описание программы), а не код, который обязан совпасть буква в букву. Если у вуза в этой предметной области есть направление под другим кодом (как у Иннополиса) — оно **годится**, это не `not_offered`.

### 1.3 subject_slugs — фиксированная таблица (для построения `olympiad_id`, см. раздел 4)

Не транслитерировать самостоятельно — использовать только эти значения, чтобы у обоих исполнителей (A+B и C) получался одинаковый слаг:

| Предмет (как в перечне/ВсОШ) | slug |
|---|---|
| Информатика | `informatika` |
| Математика | `matematika` |
| Программирование | `programmirovanie` |
| Физика | `fizika` |
| Биология | `biologiya` |
| Химия | `himiya` |
| Обществознание | `obschestvoznanie` |
| Экономика | `ekonomika` |

Если встретилась олимпиада/профиль по предмету не из этой таблицы (за пределами скоупа проекта) — добавить строку в эту таблицу по тому же принципу (латиница, транслитерация 1:1 по звучанию, без спецсимволов) и использовать её и в A+B, и в C одинаково; не изобретать разные варианты слага для одного предмета.

## 2. Датасет A — `vuz_napravleniya.json` (реальные образовательные программы по вузам)

**Зачем нужен:** это фикс проблемы с жёстким кодом (раздел 1.2) и проблемы неуникального ключа (см. п. 0.8). Вместо проверки «есть ли у вуза именно код X» — агент, уже находясь на странице правил приёма конкретного вуза, выгружает **все образовательные программы** бакалавриата/специалитета, которые по смыслу (названию/описанию) попадают в один из 4 `profile_group`. Единица учёта — программа (`program_id`), а не код направления: у одного кода может быть несколько разных программ на разных факультетах с разными списками принимаемых олимпиад (типичный случай у ВШЭ). Филиалы — отдельные вузы (п. 0.9).

**Один объект = одна реально существующая образовательная программа.** Если по `profile_group` у вуза вообще ничего нет — один объект со `status: "not_offered"`, `program_id: null` (см. пример ниже).

```json
{
  "vuz_id": "hse",
  "profile_group": "ИТ",
  "status": "offered",                 // offered | not_offered | to_check
  "program_id": "hse__pmi-fkn-moskva",
  "program_name": "Прикладная математика и информатика",
  "faculty": "Факультет компьютерных наук, Москва",
  "napravlenie_code": "01.03.02",      // классификатор ОКСО, НЕ ключ — см. пример ниже с тем же кодом на другом факультете
  "napravlenie_name": "Прикладная математика и информатика",
  "education_level": "bakalavriat",    // bakalavriat | specialitet
  "budget_places_2026": 180,
  "admission_year": 2026,
  "source_url": "https://enrol.hse.ru/upload/pravila_priema_bak_2026.pdf",
  "source_page": 12,
  "source_date": "2026-09-25",
  "is_demo": false
}
```

Тот же код ОКСО, другая программа того же вуза (тоже в Москве, не филиал) — отдельный объект, отдельный `program_id`, свой список олимпиад в датасете B:

```json
{
  "vuz_id": "hse",
  "profile_group": "ИТ",
  "status": "offered",
  "program_id": "hse__kompyuternye-nauki-i-analiz-dannyh",
  "program_name": "Компьютерные науки и анализ данных",
  "faculty": "Факультет компьютерных наук, Москва",
  "napravlenie_code": "01.03.02",
  "napravlenie_name": "Прикладная математика и информатика",
  "education_level": "bakalavriat",
  "budget_places_2026": 45,
  "admission_year": 2026,
  "source_url": "https://enrol.hse.ru/upload/pravila_priema_bak_2026.pdf",
  "source_page": 8,
  "source_date": "2026-09-25",
  "is_demo": true
}
```

Пример «в этой области у вуза ничего нет» (например, у Казанского ГМУ по группе «Экономика») — здесь `source_url`/`source_page` указывают на страницу/раздел, где перечислен полный список направлений вуза (именно там подтверждается отсутствие направления, а не на общий лендинг приёмной кампании):

```json
{
  "vuz_id": "kazan-gmu",
  "profile_group": "Экономика",
  "status": "not_offered",
  "program_id": null,
  "program_name": null,
  "faculty": null,
  "napravlenie_code": null,
  "napravlenie_name": null,
  "education_level": null,
  "budget_places_2026": null,
  "admission_year": 2026,
  "source_url": "https://kazangmu.ru/wp-content/uploads/2026/perechen-napravleniy-2026.pdf",
  "source_page": 1,
  "source_date": "2026-09-25",
  "is_demo": false
}
```

Правила:
- Если у вуза в одном `profile_group` несколько программ (разные факультеты/институты — даже под одним и тем же `napravlenie_code`, как в примере с ВШЭ) — это **несколько отдельных объектов**, не объединять. Программы филиалов сюда не входят (п. 0.9).
- `program_id` — обязателен и должен быть уникален глобально (не только внутри вуза). Формат: `{vuz_id}__{транслит-слаг названия программы}`, и если под одним и тем же названием у вуза несколько программ (разные факультеты) — добавить в слаг отличительный признак (факультет или код направления). Не использовать в качестве `program_id` просто `napravlenie_code` — он не уникален.
- `program_name` — официальное название программы **как оно указано у вуза** (может отличаться от `napravlenie_name`, если у вуза брендированное/более узкое название программы).
- `faculty` — факультет/институт, реализующий программу. Обязателен для заполнения при `status: "offered"`.
- `napravlenie_code`/`napravlenie_name` — реальный код и название направления ОКСО со страницы вуза, классификатор, не идентификатор. Может повторяться у нескольких программ одного вуза.
- `budget_places_2026` и факт существования программы нередко лежат в разных документах вуза — если так, это два разных `source_url`/`source_page` внутри одного объекта не выразить одной парой полей; в этом случае агент указывает как `source_url`/`source_page` источник самого числа `budget_places_2026` (более специфичный факт), а наличие программы как таковой подтверждает связка `program_name`/`faculty` с тем же источником, если он общий, или отдельно помечает `is_demo: true` на `budget_places_2026`, если для него точного источника не нашлось.
- Ожидаемое минимальное количество top-level объектов: 10 вузов × 4 profile_group = **40** (плюс дополнительные объекты там, где у вуза больше одной программы в группе).

## 3. Датасет B — `vuz_napravlenie_olimpiady.json`

**Источник для парсинга:** сайт вуза, раздел «Правила приёма» на 2026 год (не общий сайт вуза; правил 2027 года ещё нет — см. п. 0, пункт 7).
**Один объект = одна пара вуз + конкретное направление, найденное в датасете A.** Внутри — список принимаемых олимпиад (может быть пустым при `not_offered`).

**Ключ связи с датасетом A:** `program_id` — берётся из результата датасета A, а не из фиксированного справочника и не из `(vuz_id, napravlenie_code)` (этот составной ключ не уникален — см. п. 0.8: под одним кодом у вуза может быть несколько программ с разными списками олимпиад, как в примере ВШЭ в разделе 2). Если в датасете A по этому вузу+profile_group несколько программ — на каждую своя запись здесь, даже если у них одинаковый `napravlenie_code`.

**Важно про гранулярность внутри `prinimaemye_olimpiady`:** одна запись = одна уникальная комбинация `(olympiad_id, diploma_status)`. Если у вуза победитель и призёр одной и той же олимпиады получают разные льготы (типичный случай — МФТИ: победитель → БВИ, призёр → 100 баллов) — это **две отдельные записи** с одинаковым `olympiad_id`, но разными `diploma_status` и `benefit_type`. Не сворачивать в одну запись и не выбирать «более сильную» льготу.

**Про `source_url`/`source_page` здесь особенно важно:** льгота победителя и льгота призёра — это, как правило, соседние строки одной и той же таблицы в одном документе, поэтому у них обычно совпадающие `source_url`+`source_page` — это нормально и ожидаемо (в отличие от переиспользования общей ссылки на весь сайт «на всякий случай», что запрещено в п. 0.2). Если же в правилах отдельно вынесен список принимаемых олимпиад именно для этой программы (частый случай — приложение/таблица по конкретной программе), ссылаться нужно на эту таблицу, а не на титульный раздел документа.

```json
{

      "benefit_type": "БВИ",                  // БВИ | 100_ballov | dop_bally

      "ege_confirm_subject": "Информатика",

      "min_level_required": "I",

}
```

Пример, ради которого всё это затевалось — **тот же вуз, тот же `napravlenie_code`, но другая программа** («Компьютерные науки и анализ данных» рядом с ПМИ) и **другой** список принимаемых олимпиад (у неё, к примеру, нет отдельной льготы для призёров — только БВИ победителям, и ограничение по классу — только 11-й):

```json
{
  "program_id": "hse__kompyuternye-nauki-i-analiz-dannyh",
  "vuz_id": "hse",
  "program_name": "Компьютерные науки и анализ данных",
  "faculty": "Факультет компьютерных наук, Москва",
  "napravlenie_code": "01.03.02",
  "status": "offered",
  "admission_year": 2026,
  "checked_url": "https://enrol.hse.ru/upload/pravila_priema_bak_2026.pdf",
  "checked_page": 8,
  "checked_date": "2026-09-22",
  "budget_places_2026": 45,
  "prinimaemye_olimpiady": [
    {
      "olympiad_id": "p669-12-informatika",
      "olympiad_name_at_vuz": "Высшая проба, профиль «Информатика»",
      "min_level_required": "I",
      "diploma_status": "pobeditel",
      "benefit_type": "БВИ",
      "eligible_grades": [11],
      "ege_confirm_subject": "Информатика",
      "ege_confirm_min_score": 75,
      "source_url": "https://enrol.hse.ru/upload/pravila_priema_bak_2026.pdf",
      "source_page": 9,
      "source_date": "2026-09-22",
      "is_demo": true
    }
  ]
}
```

Обе записи имеют одинаковый `napravlenie_code: "01.03.02"` и одинаковый `vuz_id: "hse"`, но разные `program_id` и разные списки льгот — именно это раньше терялось при ключе `(vuz_id, napravlenie_code)`.

Правила:
- Если `status = "not_offered"` или `"to_check"` — `prinimaemye_olimpiady: []`, остальные поля — `null`, но `admission_year: 2026` проставляется всегда.
- `benefit_type` — строго одно из трёх значений.
- `diploma_status` — обязательное поле, даже если у вуза победитель и призёр получают одинаковую льготу (тогда просто две одинаковые по льготе записи с разным статусом — не сокращать).
- `eligible_grades` — ставить `null`, только если в правилах явно нет ограничения по классу; если правило не найдено (не проверяли) — `to_check` на уровне записи не предусмотрен, в этом случае ставить `is_demo: true` и не оставлять поле пустым без объяснения.
- `diploma_valid_years` в этом датасете больше нет — см. глобальную константу в п. 0.1.
- `checked_url`/`checked_page` (на уровне всей записи программы) и `source_url`/`source_page` (внутри каждой льготы) могут совпадать, если это один документ, но не обязаны — если список принимаемых олимпиад опубликован отдельным файлом от общих правил приёма, они будут разными, и это правильно.
- Ожидаемое количество top-level объектов = ровно количество объектов со `status: "offered"` в датасете A (плюс те же `not_offered`/`to_check` записи один-в-один перенесённые оттуда, чтобы оба датасета не расходились по составу программ). Фиксированного числа больше нет — оно зависит от того, сколько реальных программ нашлось на шаге A.

## 4. Датасет C — `olimpiady_spravochnik.json`

**Можно парсить полностью независимо и параллельно с A+B** (см. п. 0.5) — единственное условие: `olympiad_id` строится по детерминированной формуле ниже, а не придумывается на глаз, иначе id в B и C разойдутся без предупреждения.

**Источники для парсинга:** rsr-olymp.ru (перечень, приказ № 669) — базовый список, уровень и **номер олимпиады в перечне**; vserosolimp.edsoo.ru — этапы ВсОШ; официальный сайт конкретной олимпиады — актуальные даты этапов/регистрации.
**Один объект = одна олимпиада (по конкретному профилю, если у олимпиады их несколько).**

**Формат `olympiad_id` — детерминированная формула, единая для обоих исполнителей:**

- Если у олимпиады есть номер в приказе № 669 (`perechen_number_669` не `null`): `olympiad_id = "p669-{номер}-{slug-профиля}"`, где `{номер}` — число как есть, без нулей слева (например, `12`), а `{slug-профиля}` — из таблицы 1.3. Пример: `p669-12-informatika`.
- Если это ВсОШ (`perechen_number_669 = null`, `level: "ВсОШ"`): `olympiad_id = "vsosh-{slug-профиля}"`. Пример: `vsosh-biologiya`.
- Профиль в id указывается **всегда**, даже если у олимпиады формально один профиль — это убирает необходимость решать «нужен слаг профиля или нет» отдельно для каждой олимпиады, что как раз и есть источник расхождений между исполнителями.
- Номер олимпиады в перечне — это официальный публичный факт (одна и та же таблица на rsr-olymp.ru), поэтому исполнитель A+B, встретив на сайте вуза незнакомую олимпиаду, сам смотрит её номер в перечне (не ждёт готового Датасета C) и вычисляет id по той же формуле — она у обоих даст одинаковую строку без переписки.
- Никогда не строить id из транслитерации названия олимпиады напрямую («vysshaya-proba», «vp» и т.п.) — только через номер в перечне (или `vsosh`) + таблицу 1.3.

```json
{
  "olympiad_id": "p669-12-informatika",
  "name": "Высшая проба",
  "profile": "Информатика",
  "profile_group": "ИТ",
  "organizer": "НИУ ВШЭ",
  "level": "I",                        // I | II | III | ВсОШ
  "perechen_number_669": 12,           // номер в приказе №669, null для ВсОШ
  "official_site": "https://olymp.hse.ru",
  "description": "Краткое описание олимпиады (2-3 предложения).",
  "grades_eligible": [9, 10, 11],
  "cost": "free",                      // free | paid
  "etapy": [
    { "stage_name": "Регистрация", "type": "registration", "start_date": "2026-09-01", "end_date": "2026-09-25" },
    { "stage_name": "Отборочный этап", "type": "qualifying", "format": "online", "start_date": "2026-10-15", "end_date": "2026-11-20" },
    { "stage_name": "Заключительный этап", "type": "final", "format": "offline", "start_date": "2027-02-10", "end_date": "2027-02-12" }
  ],
  "source_url": "https://rsr-olymp.ru/upload/perechen_669_2025.pdf",
  "source_page": 4,
  "source_date": "2026-09-22",
  "is_demo": false
}
```

Правила:
- `type` в `etapy`: `registration | school | municipal | regional | qualifying | final`.
- `format`: `online | offline | mixed`.
- Парсить только олимпиады, чей `profile_group` пересекается со скоупом (ИТ/Физика/Биомед/Экономика) — не весь перечень из 83 олимпиад целиком.
- Если у олимпиады нет отдельного этапа регистрации (сразу тур) — просто не включать объект `registration` в `etapy`.
- Даты этапов конкретной олимпиады (не строка в перечне №669, а реальные даты тура) обычно берутся с официального сайта олимпиады — там `source_url` ведёт на страницу/новость с этими датами, `source_page: null` (это веб-страница, не PDF).
- Если организатор назвал только крайний день («регистрация до 30 ноября», «не позднее 31 марта»), `start_date: null`.
- `etapy_status`: `published_2026_27` — календарь сезона опубликован; `partial_2026_27` — опубликованы только ранние этапы, финала ещё нет (сид ставит демо-финал через месяц после последнего этапа); `previous_season`, `approximate`, `not_published`, `not_checked` — дат сезона нет, в приложении демо-даты. `etapy_checked_at` — день, когда даты сверены со страницей (по умолчанию дата сборки датасета).

## 5. Чек-лист для агента перед сдачей результата

- [ ] `vuz_id` — точно из справочника 1.1, `profile_group` — точно из справочника 1.2. `napravlenie_code`/`napravlenie_name` — реальные, взятые со страницы вуза (не подогнаны под `reference_codes`).
- [ ] `program_id` заполнен и уникален глобально при `status: "offered"`; не используется `napravlenie_code` в качестве идентификатора программы.
- [ ] Если у вуза несколько программ с одинаковым `napravlenie_code` (разные факультеты) — это отдельные объекты с разными `program_id` и `faculty`, а не один объект.
- [ ] Программ филиалов и конкурсных групп для иностранных граждан нет (п. 0.9) — `validate.py` падает, если `faculty` называет филиал.
- [ ] `faculty` заполнен при `status: "offered"`.
- [ ] У каждого `source_url` — это ссылка на конкретный документ/страницу, где буквально написан именно этот факт, а не на общий раздел «Правила приёма» вуза. Если источник — PDF, `source_page` заполнен.
- [ ] Нет случаев, где одна и та же ссылка стоит у нескольких разных по сути фактов (бюджетные места / льгота победителя / льгота призёра) только потому, что агент не стал искать точнее — либо у них общий источник (тогда это ожидаемо и допустимо), либо разные `source_url`/`source_page`.
- [ ] По датасету A: для каждого из 10 вузов есть запись по всем 4 `profile_group` (offered — с реальной программой, или явный `not_offered`/`to_check`); если у вуза в группе больше одной программы — несколько объектов.
- [ ] Датасет B построен строго по программам из датасета A (ключ — `program_id`, не `(vuz_id, napravlenie_code)`): нет записей с `program_id`, которого нет в A, и нет пропущенных offered-программ из A.
- [ ] Нет фактов без пометки `is_demo`, если источник не найден.
- [ ] Каждый `olympiad_id` (и в B, и в C) построен строго по формуле раздела 4 (`p669-{номер}-{slug}` или `vsosh-{slug}`) — ни один не собран транслитерацией названия на глаз.
- [ ] После того как A+B и C готовы (независимо от того, кто и в каком порядке их делал) — сделана сверка: join `B.olympiad_id → C.olympiad_id` не даёт пропусков. Если пропуск нашёлся — это либо опечатка в номере перечня, либо C реально не хватает олимпиады (добавить), а не повод менять правило.
- [ ] Каждая запись в `prinimaemye_olimpiady` содержит `diploma_status`; если победитель и призёр получают разные льготы — это две записи, а не одна.
- [ ] `eligible_grades` заполнен (массив классов или `null`), не пропущен молча.
- [ ] `admission_year: 2026` стоит в каждой записи датасетов A и B без исключений.
- [ ] Поля `diploma_valid_years` нигде в парсинге нет — эта норма только в глобальных константах (п. 0.1).
